# How the flow works

This is a plain-language walk-through of the flow diagrammed on the
[sequence diagram page](https://dkypuros.github.io/multicloud-gitops-design/). It describes
the experiment in [luis5tb/multicloud-gitops](https://github.com/luis5tb/multicloud-gitops/tree/rca-praxis-ols-claude-a2a-bm)
and is not official documentation.

An outside agent wants to ask Red Hat a question on behalf of a customer. Before it can ask anything, it has to prove who it is. So the first thing it does is go to Red Hat SSO, Red Hat's login service, with a client ID and a secret that were set up for it in advance. Red Hat SSO checks those and hands back a token. We call that Token A. It's a signed piece of data that says which agent this is, who issued the token, and what the token may be used for.

The agent then sends its question, with Token A attached, to MAS. MAS is the piece that decides where the question should go. Before it does anything else, it checks Token A: is the signature really from Red Hat SSO, has it expired, is it meant for this purpose, and is this particular agent on MAS's list of allowed callers. If any of those fail, the request stops there. If they pass, MAS hands the question to its own language model, which reads it and decides who should answer.

There are two possible answerers. One is Ask Red Hat, which runs on Red Hat's own infrastructure and knows Red Hat documentation and products. The other is OpenShift Lightspeed, which runs on a customer's OpenShift cluster and can look at what is actually happening on that cluster right now. MAS can send a question to one of them or to both, then combine what comes back into a single answer. Either way, MAS passes Token A along exactly as it received it. MAS never creates a token of its own, so the downstream services always see the original caller.

If the question goes to Ask Red Hat, that's nearly the whole story. Ask Red Hat checks Token A on its side, answers, and the answer goes back through MAS to the agent.

The path to OpenShift Lightspeed has more steps, because it ends with real access to a live cluster, and the cluster needs to know exactly what this caller is allowed to see. The question first passes through Praxis, a gateway in front of Lightspeed. Praxis looks at a header naming the cluster and forwards the request to that cluster's Lightspeed. In this setup, Praxis doesn't check the token itself. Lightspeed does. It verifies that Token A really came from Red Hat SSO, that it hasn't expired, and that the request is meant for this cluster.

Here is the important part. The cluster doesn't trust Red Hat SSO tokens directly. It trusts a Keycloak server that runs alongside it. So Lightspeed has to trade Token A for a token the cluster will accept. This trade is called a token exchange. Lightspeed first gets proof of its own identity from SPIRE, a service that issues identities to running software. It then sends that proof and Token A to Keycloak and asks for a new token meant for the cluster's tools. Keycloak checks Token A with Red Hat SSO, confirms the caller is real and the token is still active, and records the caller as a user it knows about. It also puts that user in a group called acme-agent-rca. Then it issues Token B, signed by Keycloak, aimed at the cluster's tool service, and carrying that group name.

From this point on, Token A is no longer used. Lightspeed's own language model decides which cluster tools to call, such as listing pods or reading events. Lightspeed calls those tools through the OpenShift MCP server with Token B attached. MCP makes sure some token is present, then passes Token B straight through to the OpenShift API server. The API server checks that Token B is signed by the Keycloak it trusts and is meant for this use, reads the group name from it, and looks up what that group is allowed to do. In this setup the group can read most things on the cluster but cannot change anything, and cannot read secrets or permissions. The API server returns only what that group is allowed to see. The results go back to Lightspeed, which writes its answer and sends it back through Praxis to MAS. MAS combines it with anything Ask Red Hat said and returns one answer to the agent.

The point of all this is that every step knows who is really asking. Red Hat SSO proves the caller's identity, MAS decides whether that caller may use the service at all, and Keycloak turns that identity into a group the cluster understands. In the end, the cluster's own permission rules decide what the caller can see, not a shared service account with broad access.

There are a few limits today. The caller is the agent itself, not a person who logged in, so the cluster can't tell which human was behind a request. A login for individual users is planned but not built. Praxis currently only routes and doesn't check tokens, so Lightspeed's check is the one that counts. One tightening of MCP's token handling is in place but hasn't been confirmed on the live cluster yet.
