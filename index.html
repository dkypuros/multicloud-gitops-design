Red Hat SSO → MAS → Ask Red Hat or OpenShift Lightspeed

The first working end-to-end flow, traced from the code and config on Luis's branch. An external agent gets a Red Hat SSO token. MAS validates it and routes the question to Ask Red Hat, to OpenShift Lightspeed, or to both. On the OLS path, Keycloak exchanges the token for one that maps to an OpenShift group and gets real RBAC. Stage 1

The agent gets a Red Hat SSO token

The UI picks the identity provider for each request with three headers. ACME then mints an agent token from a confidential Red Hat SSO client. The openid scope is required: Keycloak needs it later to call SSO's userinfo endpoint during the exchange. [...more]

Stage 2 · 2a

MAS validates the token and picks a specialist

MAS accepts tokens from Red Hat SSO prod, stage and the local Keycloak. It authorizes the token's sub against an exact allow-list and keeps the token for the run. Both specialist nodes have an empty bearer_token, so MAS forwards Token A as it is. It never mints a token of its own. [...more]

Stage 2b

The question reaches OpenShift Lightspeed

Stage 3

Lightspeed swaps Token A for a Keycloak token

This is the RFC 8693 exchange. Lightspeed proves who it is with its SPIFFE identity and passes Token A as the subject. Keycloak checks Token A with Red Hat SSO, brokers the subject through the matching identity provider, and adds group acme-agent-rca. Token A goes no further than Lightspeed. [...more]

Stage 4

Token B reaches the cluster and RBAC decides

Lightspeed's own LLM chooses which MCP tools to call. MCP requires a bearer token but doesn't validate it. It passes Token B to the API server, which trusts Keycloak through native OIDC, maps the groups claim, and applies RBAC. [...more]

What the tokens look like at each hop

Two tokens are in play. Token A comes from Red Hat SSO and reaches MAS, Ask Red Hat, Praxis and OLS. Token B comes from the local Keycloak and is the only token MCP and the API server see.

Set up once, not per request

  • Keycloak realm rca has external IdPs red-hat-sso-prod and red-hat-sso-stage. Token exchange is allowed, and each IdP has hardcodedGroups: [acme-agent-rca]. A PostSync reconciler heals realms that were imported earlier.
  • The Keycloak client lightspeed-mcp authenticates with federated JWT using OLS's SPIFFE ID. It also has standard.token.exchange.enabled and an openshift-mcp audience mapper.
  • OpenShift Authentication/cluster uses type OIDC and trusts the Keycloak issuer for openshift-mcp. It applies claimMappings.groups with the prefix keycloak:.
  • The lightspeed-mcp-rbac.yaml bindings give the mapped group the built-in view and cluster-monitoring-view roles.
  • MAS, OLS and Praxis all read the cluster id from global.olsClusters.

Gaps the demo still has

  • The caller is the agent's service account. Nobody logs in as a human: SSO user login (auth code + PKCE) is still a TODO in ACME.
  • Praxis is router-only in standalone. Nothing checks azp, so OLS's issuer and audience check is the real gate. The reason is that the Praxis image can't reach the SSO JWKS over IPv6.
  • MCP Mode A (require_oauth=true with passthrough) is in place but has not been verified live. MCP does not validate the JWT itself.
  • The orchestrator LLM writes the X-OLS-Cluster header name itself. When it got the spelling wrong, OLS delegations were dropped with a 404. The prompt and temperature 0 reduce this. The durable fix is for MAS to inject the header itself.
  • No act claim appears in Token B. Who acted for whom is recorded in the acme_audit and a2a_audit logs, which share a request_id.
