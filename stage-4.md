# Stage 4: Token B reaches the cluster and RBAC decides

This is a plain-language walk-through of one stage on the [sequence diagram page](https://dkypuros.github.io/multicloud-gitops-design/). It describes the experiment in [luis5tb/multicloud-gitops](https://github.com/luis5tb/multicloud-gitops/tree/rca-praxis-ols-claude-a2a-bm) and is not official documentation. For the whole flow, see [How the flow works](how-it-works.md).

Lightspeed has its own language model, Gemini running on Google Vertex AI. It is reached with a separate fixed key that belongs to Lightspeed. That key has nothing to do with the caller or with Keycloak. Lightspeed gives the model the question and a list of tools it can use, such as listing resources, reading events, or reading metrics. The model chooses which tools to call.

Each tool call goes to the OpenShift MCP server with Token B attached. In this setup MCP is set to refuse any call that has no token. That closes a gap where, without a token, it would have used its own service account and its own broader permissions. MCP doesn't check the token itself, though. It passes Token B unchanged to the OpenShift API server. This setting is in place but hasn't been confirmed on the live cluster yet.

The API server makes the real decision. The cluster was switched to trust Keycloak directly, and the API server keeps Keycloak's public keys so it doesn't have to ask Keycloak on every call. It checks that Token B is signed by that Keycloak and that the token is meant for the tool service, which the cluster lists as a purpose it accepts. It then reads two things from the token. The caller becomes a cluster user whose name starts with keycloak:. The group becomes keycloak:acme-agent-rca. Adding keycloak: to the front means a group from Keycloak can never pass itself off as one of the cluster's built-in powerful groups.

The cluster's permission rules, known as RBAC, are attached to that group. In this setup the group gets the built-in view role, which can read almost everything but change nothing and can't read secrets or permission settings. It also gets a separate monitoring role, because metrics sit behind their own permission check. Each permission was added after a real failure: first the model tried to list namespaces, then deployments, then metrics, and each was refused until the matching permission was granted.

The API server returns only what the group may see. The results go back through MCP to Lightspeed. Lightspeed's model writes the answer and streams it back through Praxis to MAS. Lightspeed also writes one log line for the request. It records who acted and on whose behalf, and carries a request ID that matches a line in ACME's log, so one request can be followed from start to finish without any token appearing in the logs.
